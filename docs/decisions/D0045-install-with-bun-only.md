# D0045: Install with bun alone, from GitHub; Electron from its own release; the SDKs' own agents

Date: 2026-11-24. Status: active. Task: T-0004. Changes [D0026](D0026-setup-command.md) and [D0030](D0030-console-setup.md) (what setup needs and checks). Written with the names of the rename to holm (T-0003), which runs beside it.

## Context
The owner asked for "a seamless way to run the installation process, what if the user doesn't have bun etc.". Until now the landing page and the README said `git clone … && cd … && bun install && bun run setup`, which needs git, bun, and Node 22.12 or later with npm (used once, to fetch Electron), plus Claude Code installed and logged in. The goal: a stranger on a clean Mac, Linux or Windows machine gets to a running app with one line, with nothing to install by hand but the agent's login.

## What was found
- **The agents are already in `node_modules`.** The Claude Agent SDK ships the whole Claude Code CLI as a platform package (`@anthropic-ai/claude-agent-sdk-darwin-arm64/claude`, 2.1.322 here, 320 MB unpacked), and runs it unless `pathToClaudeCodeExecutable` says otherwise. It answers `--version`, `auth status` and `auth login`. The Codex SDK depends on `@openai/codex`, whose platform package holds the native `codex` (378 MB unpacked); the runner already finds it (`codexBinary`). So nobody has to install Claude Code or Codex separately: `bun install` brings both, and only the login is the person's.
- **Node and npm were only Electron's installer.** Electron's GitHub release has a zip per OS and architecture and a `SHASUMS256.txt` (`https://github.com/electron/electron/releases/download/v45.3.1/`). A zip reader in TypeScript (`node:zlib`'s `inflateRawSync`, Bun's CRC-32) unpacks the macOS zip into exactly what Apple's `ditto` makes (`diff -r --no-dereference`: no difference, symlinks and modes included), and the app runs. Electron's macOS release is ad-hoc and linker-signed, not Developer ID signed (`codesign -dv`: `Signature=adhoc`), the same as npm's copy always was. Downloaded by `fetch`, it carries no quarantine attribute, so Gatekeeper does not stop it.
- **`bun install -g github:owner/repo` needs no git.** Bun fetches GitHub's tarball. Tried here with only `/bin` on the PATH (no git, Node or npm): `bun install -g github:kaitila/intuition` installed the app and its 112 packages, the SDKs' native binaries included, in 4.5 s from bun's cache. With a `bin` in `package.json`, bun links the command into `~/.bun/bin`. Electron, a dev dependency, is not installed, so the shell has to fetch it, as above.
- **bun's own installer** (`curl -fsSL https://bun.sh/install | bash`, https://bun.sh/docs/installation) puts bun in `~/.bun/bin` and adds it to the shell's profile. On Linux it needs `unzip`, which a fresh Ubuntu, WSL's included, may not have.
- **How comparable tools ship.** Bun, Deno, uv, rustup and Claude Code itself offer a `curl -fsSL …/install.sh | sh` line (and `irm …/install.ps1 | iex` on Windows) that downloads a per-OS binary from their releases. Claude Code's native installer is `curl -fsSL https://claude.ai/install.sh | bash` (https://docs.claude.com/en/docs/claude-code/setup). Homebrew taps (`brew install owner/tap/name`, a `homebrew-tap` repository with a formula or cask), winget (a manifest merged into `microsoft/winget-pkgs`) and scoop (a bucket repository) each need a repository or a review the owner keeps up. A Mac app downloaded in a browser (.dmg or .zip) gets the quarantine attribute, and Gatekeeper refuses it unless it is signed with a Developer ID and notarized (Apple Developer Program, USD 99 a year, `notarytool` in CI with an app-specific password or API key).
- **`bun build --compile`** makes one executable per OS and architecture, cross-compiled with `--target=bun-darwin-arm64` and the like. The Agent SDK's README has a section on it: the CLI binary must be embedded as a file and extracted with `@anthropic-ai/claude-agent-sdk/extract` (`extractFromBunfs`), since a child process cannot run from Bun's `$bunfs`. The Codex SDK takes `codexPathOverride`. Embedding both agents makes each executable about 700 MB. Not embedding them means fetching the matching platform packages from npm's registry at setup, or using the person's own `claude` and `codex`, whose versions drift from the SDKs'. The app also reads its own files from the repo folder at run time: the pages (`src/web`), the build id's hash, the shell's bundle (`Bun.build` of `shell/src` at install), and the shell starting the runner as `bun <repo>/src/cli.ts start` (the `wsl` and `local` runner settings). A compiled app changes all of those, and the shell's settings contract with them.

## Decision
1. **The install line needs only bun's installer**, and it is the same on every OS (on Windows, in a WSL terminal):
   ```sh
   curl -fsSL https://bun.sh/install | bash && export PATH="$HOME/.bun/bin:$PATH" && bun install -g github:kaitila/holm && holm setup
   ```
   Someone with bun already types only the second half. `package.json` has `"bin": { "holm": "src/cli.ts" }`, so bun links `holm`. The app lives in bun's global folder (`~/.bun/install/global/node_modules/holm`), and every path it reads from "the repo" is that folder: nothing else changes. `git clone` stays the way to work on it.
2. **Electron comes from its GitHub release**, unpacked by `src/shell/unzip.ts` into `<shell>/node_modules/electron/dist`, the folder npm's installer used. The zip must match the SHA-256 pinned in the repo for each layout's zip (`PINNED` in `src/shell/electron-fetch.ts`, copied from the release's `SHASUMS256.txt`), and the release's list must agree. So a mirror or a release that serves another zip with a matching list is refused, which a list fetched from the same host alone could not do. A zip with no pin (armv7l) is checked against the list alone, and says so. Bumping Electron means adding its sums; a test checks they are there. It is unpacked in a folder beside `dist`, on the same disk, and swapped in with one rename, so a stop part-way never leaves a half-written `dist` that counts as installed. So the executable's path and `dist/version` (how `isCurrent` tells the version) are unchanged. `ELECTRON_MIRROR` points it at a mirror, as for Electron's own installer. The unpacker refuses an entry that would land outside the folder before writing anything: an absolute path, `..`, a backslash, a write through one of the zip's own symlinks, or a symlink that ends outside once the zip's other links on its way are followed, as the OS would (a chain such as `s/up -> ..`, `deep -> s/up/..`), or loops. It inflates no entry past its stated size and checks every entry's CRC-32. windows-wsl fetches the `win32-x64` zip from WSL and writes it to the Windows disk.
3. **No Node, npm or git is needed.** doctor and setup no longer check Node or npm. git is shown but optional: only a git checkout needs it, to update.
4. **Claude Code is the Agent SDK's own.** doctor asks that binary for its version and login (`claudeBinary`), and uses `claude` on the PATH only when it is missing. `holm login` runs its `auth login` on the terminal; `holm login codex` runs the SDK's `codex login`. On a terminal, setup offers the login when it is missing ("Log in to Claude Code now?", yes by default) and checks again afterwards. It never logs in without that yes, and `--yes` only warns, with the command.
5. **Updates: `holm update`.** A git checkout pulls (`--ff-only`) and runs `bun install`. A package in bun's global folder is installed again with `bun add --global github:kaitila/holm`. Any other copy (an unpacked archive) is left alone, with what to do. Either way, `holm up` then runs from the new code, which restarts a runner and a shell older than it (D0011). `holm uninstall` says the last step for a package install: `bun remove --global holm`.
6. **Releases: none needed yet.** The line installs the default branch, as `git pull` did. CI's macOS and Linux shell jobs already install the shell through `shell install`, so they fetch Electron the new way on every run. Their `setup-node` step is now unused; removing it is left to the owner, since changing a workflow file needs a GitHub token with the `workflow` scope.

## Still by hand
- **Windows:** WSL itself (`wsl --install` in an administrator terminal, then a restart and the distribution's first start), and `sudo apt install -y unzip` in it before bun's installer. A WSL distribution has no installer that can run before it exists.
- **Linux:** `unzip`, if missing (bun's installer says so).
- **Every OS:** the agent's login (Claude Code's `auth login`, a browser page; or Codex's), which setup offers to run.
- **macOS:** Screen Recording for the snip (System Settings), as before.

## Proposed, not built: they need the owner's say
These break a rule in AGENTS.md or need the owner's accounts, so they are written down here and not done:
- **A `curl | sh` line of our own** (`https://kaitila.github.io/holm/install.sh`): a POSIX `sh` script of about 30 lines that picks the OS and architecture and downloads a compiled `holm` from the latest GitHub Release, then runs `holm setup`. It needs an exception to "no bash files". It removes the PATH export and bun's `unzip`. With item 2 below, it would also remove bun. A Windows `install.ps1` would need a PowerShell exception too, and still cannot install WSL without a restart.
- **Compiled binaries** (`holm-darwin-arm64`, `holm-darwin-x64`, `holm-linux-x64`, `holm-linux-arm64`), built by a release workflow on a `v*` tag with `bun build --compile --target=…`, uploaded to a GitHub Release with a `SHA256SUMS`. That needs code first: pages served from embedded files, a build id from the version, the shell's bundle built at release time, the runner location in the shell's settings naming the binary rather than `bun` and a repo (a contract change), and the agents fetched at setup from npm's registry, version-pinned to the SDKs' (a tarball reader beside the zip reader). No new dependency is needed; it is a large change and its own task.
- **A Homebrew tap** (`kaitila/homebrew-tap`, `brew install kaitila/tap/holm`): a repository the owner creates, with a formula that depends on `bun` and runs the same global install. It needs no exception, but someone has to keep it up.
- **A signed and notarized Mac app** (.dmg with Electron, the runner inside): an Apple Developer ID, notarization in CI (secrets: the certificate, its password, an App Store Connect API key) and an app bundle of our own. It is the only route that works by double-click. It also fixes "Electron" being the name in Screen Recording's list.
- **winget and scoop** make sense only once there is a Windows binary. With the runner in WSL, there isn't one.

## Risk
- `github:kaitila/holm` installs whatever is on `main`: a broken merge reaches anyone who installs or updates then. Tags (`#v0.2.0`) can pin it once releases are cut.
- The global install is large (the two agents' binaries, about 700 MB unpacked, once). `holm update` downloads them again only when the SDKs' versions change (bun's cache).
- The Agent SDK's Claude Code and a separately installed `claude` share the login (the keychain and `~/.claude`), so logging in with either does both. Their versions can differ; the runner uses the SDK's, as it already did.
- Tried on this Mac only (darwin-arm64): the fetch, the unpack, `shell install`, doctor and `setup --yes` (linux layout, no display) from a package installed with only bun on the PATH. Not tried: a clean Linux machine, WSL (the `win32` zip written to `/mnt/c`), and an x64 Mac.
