# The Windows shell

An Electron app in TypeScript (`shell/src/`) that lives in the tray. It does what a web page can't: the global hotkeys, the clipboard capture, the snip (a frozen screen to draw an area on), the tray icon, the dock at the top of the screen, and small windows on the runner's pages. Why Electron: [D0001](decisions/D0001-runner-web-shell.md). What it sends the runner: [protocol](protocol.md).

It is installed and started from WSL. Nothing is built or run with the Node on the Windows side.

The commands below are written `intuition …`. That command exists once `bun src/cli.ts link` has been run in the repo, one time ([README](../README.md), "Setup"); before that, or without it, `bun src/cli.ts …` from the repo does the same. The shell itself never uses the link: it starts the runner with bun and the repo's path ("Starting the runner" below).

## Install, start, stop
| Command | What it does |
|---|---|
| `intuition up` | The one command: starts the runner (`intuition start`), installs the shell if it is not installed, writes the `wsl` settings below, and starts the shell. When the installed bundle differs from what `shell install` would write now (after a pull that changed `shell/src/`, or an install from before the dock), it asks the running shell to quit, waits up to ten seconds for its process to end (the shell keeps its pid in `shell.pid` beside its settings), installs and starts it. A runner older than the repo is restarted first, or kept while sessions run ([D0011](decisions/D0011-stale-runner-and-shell.md)); a kept runner does not stop the shell's update, and `up` exits 3. |
| `intuition shell install` | Bundles `shell/src/main.ts` into one file, `main.cjs`, and the preload scripts of the dock and the snip into `dock-preload.cjs` and `snip-preload.cjs`, and copies them with `shell/package.json` to `%LOCALAPPDATA%\intuition\shell`. The first time, it also installs Electron there for Windows (npm and node from WSL, with `npm_config_platform=win32` and `npm_config_arch=x64`): a download of about 130 MB. Later installs only replace the bundle, unless `shell/package.json` pins another Electron version. It also writes where the runner lives into the shell's settings (`wsl`, below). |
| `intuition shell start` | Starts `electron.exe` on that folder and leaves it running. If the shell already runs, this opens its chat window instead. |
| `intuition shell stop` | Asks the running shell to quit. Does nothing when none runs. |
| `intuition shell login on` | Start the shell when you log in to Windows. `off` turns that off, `status` says which it is. See "Start on login" below. |
| `intuition shell selftest` | The same as `bun src/shell/selftest-run.ts`, below. |

After installing again, stop and start the shell: a running one keeps the old bundle.

## Settings
The person's settings live in the runner, not in the shell: the Settings window (tray > Settings…), the tray's checkboxes and the runner's `/api/settings` all change the same values, and the shell applies every change at once, without a restart. Why it is built this way: [D0021](decisions/D0021-shell-settings-from-the-runner.md). The API is in [protocol](protocol.md) under "Settings".

What the shell applies, from the runner's settings:
- `shell.hotkey`: an [Electron accelerator](https://www.electronjs.org/docs/latest/api/accelerator) that captures the clipboard and opens the pop-up. `Control+Alt+Space` by default.
- `shell.snipHotkey`: an Electron accelerator for the snip (below). `Control+Alt+S` by default.
- `shell.dock`: whether the dock is shown. On by default.
- `shell.startOnLogin`: whether Windows starts the shell at login (see "Start on login").
- `theme` (`system`, `light` or `dark`): the theme of the shell's windows, through `nativeTheme.themeSource`. Their title bars, scrollbars and the pages' `prefers-color-scheme` follow it.

**How it hears of a change.** The shell keeps one WebSocket to the runner's `/ws` open in its main process. On every connect it asks `GET /api/settings`, and it applies each `{ type: "settings" }` message. When the socket closes (the runner stopped or restarted) it connects again after 1, 2, 4 and 8 seconds, then every 15, without a word. The socket never starts the runner.

**A hotkey change** registers the new hotkey first and releases the old one only once that has worked. If the new one cannot be registered (another program holds it, the other hotkey is the same, or it is not a valid accelerator), the old one keeps working. A notification names the hotkey that failed and the one that still works: "intuition: the hotkey could not be set" (or "the snip hotkey"). The two hotkeys can trade keys in one change.

**The tray's checkboxes** ("Show dock", "Start on login") write to the runner (`GET`, then `PUT` of the whole settings) and apply what it stored, so the tray and the Settings page always agree. If the runner does not answer, or is older than the shell and has no settings, nothing changes and a notification says so ("the setting was not changed").

**Before the runner answers** at the shell's start, the hotkeys are the old file's values if it still has them, else the defaults, and they move as soon as the runner's settings arrive.

### The shell's file
`%APPDATA%\intuition-shell\settings.json` keeps two keys. It is written with the first one on first start:

```json
{
  "runnerUrl": "http://127.0.0.1:4777",
  "wsl": {
    "distro": "Ubuntu",
    "repo": "/root/projects/intuition",
    "bun": "/root/.bun/bin/bun"
  }
}
```

- `runnerUrl`: where the runner listens. The shell's windows load this origin and nothing else. Stop and start the shell after changing it.
- `wsl`: where the runner lives, so the shell can start it. Not in the defaults: `shell install` and `up` write it, from `WSL_DISTRO_NAME`, the repo the command was run from and the bun that ran it, and keep everything else in the file. `distro` is letters, digits, `.`, `_` and `-`; `repo` and `bun` are absolute WSL paths. Run from a git worktree, the command writes that worktree's path.

A value that is missing or malformed falls back to its default. A `wsl` with any part missing or malformed counts as absent, and the shell then starts no runner.

**The migration from an older shell.** A file from before the runner kept the settings may also have `hotkey`, `snipHotkey` and `dock`. The first time the shell finds that the runner has no shell settings yet (`shell` is null), it sends those values, the defaults for any it lacks, and start on login as Windows has it now. Once the runner has stored them, it rewrites the file with `runnerUrl` and `wsl` alone. This happens once: after that, the runner's values are the ones applied. If the runner refuses the old values (a hotkey it does not accept), the shell sends the defaults instead.

## What it does
- **Tray**: an icon with a menu: New task, Snip, Open chat, Settings…, a "Show dock" checkbox, a "Start on login" checkbox, Quit. Both checkboxes write to the runner (see "Settings"). A double-click opens the chat. There is no window at start.
- **Hotkey, and New task**: captures the clipboard and opens the pop-up, both at once. The pop-up is a frameless 560x380 window, always on top, on the runner's `/prompt`, in the middle of the display the cursor is on. Esc or a click elsewhere hides it. Pressing the hotkey while it is up focuses it. The page closes it with `window.close()`.
- **Clipboard capture**: an image is saved as `%TEMP%\intuition\clip-<time>.png` (the newest 20 are kept) and its Windows path posted to `/api/clipboard` as `{ imagePath }`. Otherwise the text, cut to 20,000 characters, as `{ text }`. An empty clipboard posts `{}`. When the clipboard holds both an image and text, the image wins.
- **Snip hotkey, and Snip**: freezes every display and lets the person drag an area and type the task right beside it. See "The snip" below.
- **Links elsewhere**: a link from one of the runner's pages to `http:`, `https:` or `mailto:` on another origin opens in the default browser (`shell.openExternal`), from a new window or a link followed in the page. Anything else (`file:`, `javascript:`, other protocols, a URL with a user name or password, a redirect) opens nothing.
- **Settings…**: a normal 720x640 window titled "intuition settings", on the runner's Settings page (`/assets/settings.html`). It is focused if already open. A link from any of the runner's pages to `/settings` or `/assets/settings.html`, opened in a new window or followed in the page, opens this window.
- **Open chat**: a 1100x720 window on `/`, or `/?session=<id>` (`electron.exe <app> --session <id>`, and a link to `/?session=<id>` that a page, the dock among them, opens in a new window). Focused if already open.
- **Runner not running**: when `GET /health` does not answer within 1.5 seconds, the shell starts the runner itself: at its own start, on the hotkey and New task, and on Open chat (the dock's links to the pop-up and the chat among them). It runs `wsl.exe -d <distro> --exec <bun> <repo>/src/cli.ts start --login-env` from its `wsl` settings, with no window, and asks `/health` again for up to ten seconds. The pop-up or the chat then opens as if the runner had been there; the clipboard was read when the key was pressed and is posted once the runner answers. If nothing answers after ten seconds, or there are no `wsl` settings, no window opens and a notification says the runner is not running. See "Starting the runner" below.
- **Dock**: a clear window on the runner's `/dock` page at the top centre of the primary display, in which the page draws an island that grows when something happens or the pointer rests on it. It shows what the sessions are doing, in place of the Windows toasts the shell used to show. See "The dock" below.
- **Notifications**: only for the shell's own trouble: the runner is not running, the runner is older than the shell (it answers but has no dock), a hotkey could not be set, a tray checkbox could not be saved, start on login could not be changed. Never for a session.
- **One instance**: a second copy hands its command line to the first and exits. That is how `shell stop` works (`--quit`).

## Starting the runner
- **The command.** `wsl.exe` is given an array of arguments and `--exec`, so neither Windows nor a shell in WSL reads the settings' values as a command line: a path with spaces, quotes or `;` stays one argument. A `wsl` setting that could be read as an option (a name starting with `-`, a path not starting with `/`) is refused when the settings are read. Why: [D0006](decisions/D0006-start-stop-and-login.md).
- **The environment.** `--login-env` makes `start` run the runner through your login shell (`zsh -l -i -c …` or bash's equivalent), so sessions get the PATH your terminal has. Whatever your profile prints lands at the top of the runner's log (`intuition logs`). A profile that takes several seconds leaves less of the ten. A profile that replaces the shell with another program (`exec tmux`) would keep the runner from starting: start it from a terminal then.
- **Ten seconds may be short.** On this machine the command took about six seconds with WSL already up, four of them the profile. Right after a login WSL itself has to boot first, so the first notification may say the runner is not running although it comes up moments later; the next hotkey press finds it. This has not been tried after a real login.
- **A runner that dies later** is not restarted by the dock's check, which only hides the dock: the runner starts again at the next hotkey, New task or Open chat, and the dock comes back with it.
- **`bun scripts/smoke-start.ts`** runs that very command through the real `wsl.exe` for a runner in temp folders on a free port with the fake agent, and checks that the runner is still up, as its own process and with the login shell's PATH, after `wsl.exe` has returned. It needs Windows and is skipped in CI. It passed on this machine on 2026-11-13. It does not involve Electron: the shell's own spawn of `wsl.exe` (no window, from a Windows program) has not been seen.

## Start on login
- **On and off.** The "Start on login" checkbox in the tray menu or on the Settings page, or `intuition shell login on` and `off` from WSL. `intuition shell login status` only reads. The checkbox and the page change the runner's `shell.startOnLogin`, and the shell sets the login item from there. `shell login on|off` sets the login item and then tells the runner, if it answers, so a running shell does not set it back. All of them use Electron's login item (`app.setLoginItemSettings`), which is a value named `intuition` under the Windows user's `Run` registry key: `"<…>\electron.exe" "<…>\intuition\shell"`. Windows lists it under Task Manager > Startup apps, where it can also be switched off.
- **At login** Windows starts the shell, and the shell starts the runner as above. WSL has to boot first, so allow some seconds.
- **The command and a running shell.** `shell login on` works whether or not the shell runs, and a running shell's checkbox follows it. It needs the installed bundle to know `--login`: after updating the repo, `shell install` first.
- **It names the installed folder,** not the repo: installing again does not change it. Removing `%LOCALAPPDATA%\intuition` while it is on leaves a login item that starts nothing: turn it off first.
- **Nothing automatic turns it on.** Not the install, not `up`, not the self-test (which reads it and prints which it is, and never applies the setting), not any test or script. The migration sends the runner what Windows has, so it changes nothing either.

## The dock
The contract between the page and the shell is in [protocol](protocol.md) under "Dock". This is the shell's half: the window. The page (`/dock`) is the runner's.

- **The window.** Frameless and clear (the page draws the island; the rest of the window shows what is behind it), no shadow, always on top, not in the taskbar or Alt+Tab, not movable or resizable by the person. It touches the top edge of the primary display, centred, placed from the display's bounds and not its work area, so a taskbar at the top does not push it down. It is centred again when a display is added or removed or its resolution or scale changes.
- **One size, three states.** The window is 460x480 for its whole life (`DOCK_WINDOW` in `shell/src/dock.ts`; `dockBounds` there is the one function that says where it goes, and it takes no state). The shell never resizes or moves it for a change of state. In each state the island stays inside a rectangle at the top centre of the window: idle 128x22, peek 380x40, open 460x480 (`DOCK_SIZES`, `islandRect`).
- **The mouse.** The window lets the mouse through to whatever is under it (`setIgnoreMouseEvents(true, { forward: true })`), except while the cursor is on the island's rectangle for the state the page last reported. The main process decides: it looks at the cursor every 20 ms while it is within 160 pixels of the island and every 120 ms otherwise (`watchMs`), and switches when `takesMouse` changes. Letting the mouse through is the default: from the moment the window is created, and again whenever the page starts over, fails to load, crashes or is hidden, the shell holds no state for it, and with no state nothing takes the mouse. A broken page cannot block a click at the top of the screen.
- **The page decides.** It calls `window.intuitionDock.setState("idle" | "peek" | "open")` and the shell takes that as where the island is, for the mouse and the keyboard. That function is all the bridge has: `shell/src/dock-preload.ts`, the only preload script in the shell, given only to the dock's window. The main process takes a call only from the dock window's main frame, on the runner's origin, with one of the three values; anything else changes nothing and is not answered.
- **The keyboard.** In idle and peek the window cannot be focused: showing it, the island growing or a click on it takes nothing from the program the person is typing in. Only in open can it take the keyboard, when the person clicks into it; the shell never focuses it itself. Going back to idle or peek while it has the keyboard gives the focus back to the window below.
- **Its links.** A link the page opens in a new window to `/?session=<id>` opens the chat window on that session, and one to `/prompt` captures the clipboard and opens the pop-up, as the hotkey does. Every other new window is refused.
- **When it shows.** At the shell's start once the runner answers, and whenever the shell has started the runner. Every 4 seconds the shell asks `/health`: after two misses in a row the dock is hidden; when the runner answers again the page is loaded afresh and the dock shown, idle. A page that does not load (no answer, an HTTP error such as a 404 from a runner that has no `/dock` yet, a crashed page) hides the window: an empty clear window is never left on screen. The shell tries again at the next check. When the page fails with an HTTP error while `/health` answers, the runner is older than the shell: a notification says so once ("run intuition up"), and the dock appears by itself at the first check after the runner is restarted.
- **Off.** Untick "Show dock" in the tray or turn the dock off on the Settings page: the window is closed at once, not hidden, and nothing is created at the next start. Turned on, it loads and shows at once. With the dock off the shell shows nothing about sessions at all; the chat window still has everything.

### Why
The decisions are [D0008](decisions/D0008-dock.md), which replaces the shell's half of [D0005](decisions/D0005-toasts.md), and [D0010](decisions/D0010-dock-fixed-window.md) for the window's one size and the mouse. The window's reasons:
- **A dock instead of toasts.** The owner asked for it: a pill at the top of the screen that expands on hover, "like the apple style dynamic island almost", where a session can be continued. A toast can't be replied to, Windows decides whether it shows at all (Do Not Disturb, notification settings, an app id without a Start-menu shortcut), and in all the time the shell had toasts nobody saw one. The dock is the shell's own window: what it shows is up to the page.
- **The page decides the state, through a one-function bridge.** Hover, a finished session and an open approval are things the page knows; the shell only knows the window. The bridge is one-way and carries one word: a page that went wrong, or a frame inside it, can at worst name another of the three rectangles. The dock keeps the sandbox, context isolation and no Node, like the other windows; the preload is the single addition.
- **The window never resizes; the mouse goes through it.** It used to be resized for every state, and on a real desktop that was the jank the owner saw: Windows resizes a clear, frameless window slowly and out of step with the page animating in it. Now the page alone animates. The old fear of an overlay, a clear part of the screen that swallows clicks, is answered by who decides and what the default is: the main process reads the cursor itself on a timer, so no missed mouse-leave and no hung page can leave the window taking clicks, and a page that has reported nothing, or has gone away, takes none.
- **Not focusable until open.** A window that appears by itself (a session finished) or under the mouse (hover) must not take the keyboard from someone mid-sentence. Windows gives that guarantee only to a window that cannot be activated at all, so that is what the dock is in idle and peek.
- **The display's bounds, not the work area.** The island belongs on the very top edge, also over a maximised window's title bar.
- **Two misses before hiding.** One slow `/health` (the runner busy starting a session) would otherwise blink the dock away and reload its page.

## The snip
The snip hotkey (`snipHotkey`, `Control+Alt+S` by default) or the tray's Snip. Like Windows' Win+Shift+S, but the task is typed right where the area was drawn. Why it is built this way: [D0014](decisions/D0014-snip.md).

- **The windows.** One overlay per display: frameless, always on top (above the taskbar), not in the taskbar, covering the display's bounds, on the runner's `/assets/snip.html`. They are made and loaded ahead, hidden, once the runner answers, and again right after each snip and whenever a display is added, removed or changed. If none are ready (the runner was down), the key makes them then and starts the runner as the hotkey does.
- **The key.** The shell captures every display with one `desktopCapturer` call, sized to the largest display at its native resolution, hands each overlay's page its own display's image (`getCapture()`, a JPEG data URL), waits until each page says its image is drawn (1.5 seconds at most), and shows them all. The one under the cursor takes the focus. Pressing the key while a snip is up focuses it again.
- **The page.** The frozen screen, slightly dimmed, with a crosshair. A drag draws the selection: undimmed, a hairline in the accent colour, and its size in device pixels small at its top left corner. A click without dragging (under 4 pixels) selects the whole display. On release a compact box appears below the selection, left edges lined up (above it when there is no room below; inside it, at its bottom and centred, when there is room on neither side), with the focus in it. The box has the task (one line, growing to five), the workspace as a chip (the last one used; Tab and Shift+Tab, Alt+1..9 or a click switch it), and a status line. Dragging again replaces the selection and keeps the text. A press on another display moves the selection there; the text typed on the first stays in its own box.
- **Enter.** The page asks the shell to crop (`crop(rect)`, in CSS pixels of the overlay, which are the display's DIPs). The main process checks the rectangle, cuts it from the capture at the display's device pixels (edges rounded outwards), saves it as `%TEMP%\intuition\snip-<time>.png` and answers its Windows path. The snips are pruned with the clipboard's clips: the newest 20 of both, together. The page then starts the session with `POST /api/sessions { workspace, prompt, imagePath }`, and all overlays close. An error (a refused crop, an unreachable runner, a 400) shows in the box's status line, and the text stays to send again. A failed send does not save the same selection twice.
- **Esc** closes every overlay, from the page or, if the page does not answer, from the main process (`before-input-event`). An overlay that closes or crashes closes them all.
- **The bridge.** `shell/src/snip-preload.ts`, given only to the overlay windows, puts `window.intuitionSnip` in the page with `getCapture()`, `crop(rect)` and `close()`, and nothing else. The main process answers only one of its own overlay windows, from its main frame, on the runner's `/assets/snip.html`. `crop` takes an object with exactly `x`, `y`, `width` and `height`, finite numbers, at least one pixel, inside the display (`acceptedRect` in `shell/src/snip.ts`), and nothing else. The file is written by the main process alone, under `<temp>\intuition`, named from the clock.
- **Locked.** With Windows on its lock screen the capture comes back empty: the page says nothing was captured, and Esc closes it.
- **The time.** On this machine (three displays, one at 200%) the overlays were up 570 to 640 ms after the call, about 430 ms of that the capture itself. The spec aims for 300 ms. The self-test prints the time.

## What pages can do
The windows are sandboxed, with context isolation and no Node integration. Two have a preload script: the dock's, which gives its page `window.intuitionDock.setState` and nothing else (see "The dock"), and the snip overlays', which gives theirs `window.intuitionSnip` with `getCapture`, `crop` and `close` (see "The snip"). Navigation or a redirect to any origin but the runner's is refused, and so is every new window but two: a link to the runner's own chat view opens in the chat window, and the dock's link to `/prompt` opens the pop-up. A link to `http:`, `https:` or `mailto:` elsewhere goes to the default browser instead (see "Links elsewhere" above). Pages get no permissions (camera, location, notifications and the rest) except writing to the clipboard. There is no application menu, so no reload or developer-tools shortcuts.

## Self-test
`bun src/shell/selftest-run.ts` runs on this machine only (it prints `skipped` and exits 0 when `CI` is set or there is no `/mnt/c`). It installs the shell, starts a stub runner on a free port, runs `electron.exe <app> --self-test <result file> --runner-url <stub>`, and checks the JSON the shell writes. The self-test uses its own user data folder and its own hotkeys (`Control+Alt+Shift+F11`, and `Control+Alt+Shift+F10` for the snip, and `Control+Alt+Shift+F12` as the changed one), so it runs beside a running shell. It shows no notification: the ones it would show are noted and checked. It opens no browser: the links it tries are only noted. It puts text and then a small image on the clipboard, then puts back what was there (text or an image; other kinds, such as copied files, are not put back). The pop-up flashes on screen for about a second, without taking focus, and so does the chat window. The dock's window is up for some seconds at the top of the screen, with nothing to see in it: the stub's dock page draws no island. The self-test crashes that page's process once, on purpose. Every display then shows the snip's frozen overlay twice, for under a second each. Last, the dock comes and goes again, and the Settings window and the chat flash up. Run with Windows on its lock screen, the clipboard steps fail, because nothing can use the clipboard there; the runner says so in a note.

What it covers, on the real Windows desktop:
- a global hotkey registers;
- the tray icon is created (then removed at once);
- a text clipboard is captured and posted, and the stub runner received it;
- an image clipboard is captured, saved as a PNG under `%TEMP%\intuition`, and its path posted; the file exists under `/mnt/c` and starts with the PNG signature (the test then deletes it);
- Windows says notifications are supported;
- the pop-up is created at 560x380 (a pixel either way: on a display at 200% left of the primary one Electron reads it back as 559x380), loads `/prompt`, is visible, and is centred on the display under the cursor;
- a navigation and a new window to another origin are both refused as windows; the links the pages try that the shell would hand to the browser are exactly the `http`, `https` and `mailto` ones, and `file:`, `javascript:` and `ftp:` are not among them;
- `window.close()` from the page closes the pop-up;
- with no runner answering, no window opens (the self-test has no `wsl` settings and never starts a runner);
- start on login can be read (`app.getLoginItemSettings`). The result's `openAtLogin` says which it is on this machine, and either passes. The self-test never sets it;
- the dock, against the stub runner's own tiny `/dock` page:
  - with `"dock": false` no dock window is created;
  - a dock window with no page in it yet ignores the mouse, with the cursor right where the island will be. (The self-test cannot move the real cursor: it gives the shell's own cursor watching a made-up position and reads what the shell last told the window.);
  - otherwise it is created, loads `/dock`, is shown, and is neither focusable nor focused; its bounds are its one place at the top centre of the primary display (checked in WSL with `dockBounds` on the display the shell reported);
  - idle: the cursor on the pill's rectangle is taken; far away, and just below the pill inside the window, it is ignored;
  - the page sees `window.intuitionDock` with `setState` alone, and no `require` or `process`;
  - after `setState("peek")` the bounds are the same, the window is not focusable, and the cursor is taken on the peek's rectangle and ignored below it; after `setState("open")` the bounds are the same again, the window is focusable, and the point below the pill is taken now; a call with a value that is not a state changes nothing; after `setState("idle")` the bounds are still the same and it is not focusable;
  - a page that loads and never calls `setState` leaves the window ignoring the mouse; and when the page's process is crashed the window hides and ignores the mouse;
  - a call from a page on an origin that is not the runner's changes nothing. (The shell is told for that moment that its runner is at `localhost`, so the same page at `127.0.0.1` is the foreign one. No second server is involved.);
  - the page's new-window link to `/?session=self-test-session` opens the chat window on it, its link to `/prompt` opens the pop-up, and links to another of the runner's paths and to another site open nothing;
  - with no runner answering, the dock is still there after one check and hidden after the second; with the runner back, the next check loads the page and shows it, idle;
- the snip, against the real `/assets/snip.html` (the stub serves `src/web`'s files):
  - its own snip hotkey registers;
  - with the overlays made ahead, as in a running shell, opening it puts one overlay on each display, its content exactly at the display's bounds, shown and on top, on `/assets/snip.html`. The time from the call is printed, with when the capture and the drawing were done; only more than 3 seconds fails;
  - the page sees `window.intuitionSnip` with `close`, `crop` and `getCapture`, and no `require` or `process`;
  - `crop` of a known rectangle (10.5, 20.25, 101x49.5 DIPs) saves `<temp>\intuition\snip-<time>.png`, and its PNG header has the size that rectangle has at the first display's scale (the test then deletes it);
  - `crop` with a negative or too large rectangle, `NaN`, `Infinity`, a string, a zero width, an extra key, `null`, an array or a path is refused, every time;
  - the page's `close()` closes every overlay, and so does Esc sent to one as a key;
  - when the capture comes back empty (a locked desktop) it fails with one line that says so, and does not judge the crop;
- settings, against the stub runner's `GET` and `PUT /api/settings` and its `/ws`. Each PUT is sent to every socket as a `settings` message, as the real runner does. The self-test changes the settings as the Settings page would (GET, change, PUT), so the shell hears of each change only through its socket:

## Hand-test checklist
Steps 10 to 18 are the dock, step 9 is the shell starting the runner, steps 20 to 23 are start on login, steps 24 to 31 are the snip, and steps 32 to 37 are the settings: nobody has seen any of them yet. The dock steps need a runner that serves the dock's page (`/dock`): with an older runner, step 10 shows no dock at all, and that is right.

1. In WSL: `intuition shell install`, then `intuition up`. **See**: a line `intuition runner on http://127.0.0.1:4777 …`, and a small blue-violet disc in the tray (maybe under the `^` arrow), with the tooltip "intuition". No window but the dock (step 10).
2. Copy some text anywhere, then press Ctrl+Alt+Space. **See**: a small window without a title bar in the middle of the screen the mouse is on, above other windows, with the keyboard focus in it. In WSL, `curl http://127.0.0.1:4777/api/clipboard` shows the text.
3. Press Ctrl+Alt+Space again. **See**: the same window, still there and focused, not a second one.
4. Press Esc. **See**: the window gone. Press the hotkey, then click on another window. **See**: gone again.
5. Take a screenshot to the clipboard (Win+Shift+S), then press the hotkey. **See**: the pop-up, and a new `clip-<time>.png` in `%TEMP%\intuition` that shows the screenshot.
6. Right-click the tray icon. **See**: New task, Snip, Open chat, Settings…, a ticked "Show dock" checkbox, a "Start on login" checkbox, Quit. Choose New task. **See**: the pop-up, as in step 2.
7. Double-click the tray icon. **See**: a normal window, about 1100x720, titled "intuition", on the chat view. Double-click again. **See**: the same window brought to the front, not a second one.
8. On a second display, if there is one: move the mouse there and press the hotkey. **See**: the pop-up in the middle of that display.
9. `intuition stop` in WSL, then press the hotkey. **See**: no console window flashing; within about ten seconds, the pop-up, with the clipboard attached. `intuition status` in WSL says `running`. (If instead a notification says the runner is not running, wait a few seconds, press again, and look at `intuition logs`: note how long the start took.)
10. The dock, idle. With the runner and the shell running, look at the top of the primary display. **See**: a small faint tab with a dot in the middle, touching the top edge, about 30 wide and 16 tall, above every other window, a maximised one too. Around it nothing: no rectangle, no border, no shadow, and what is behind shows through. Click right beside it and just under it, on a browser tab or a title bar. **See**: every click lands on what is there. Nothing new in the taskbar or in Alt+Tab. Type in another program while it is there. **See**: the typing goes where it went before; that program's title bar stays lit.
11. Hover. While typing in another program, move the mouse onto the pill, without clicking. **See**: after a moment it grows downwards, smoothly and as one shape, into a panel 460 wide and as tall as its content (480 at most), still centred, with the sessions in it; the text fades in as the shape arrives. No stutter, no flicker, no jump. A mouse that only crosses the tab on the way elsewhere opens nothing. The other program is still the active one: its title bar stays lit, a key pressed now still lands in it, and nothing flashes in the taskbar. Move the mouse away. **See**: it shrinks back to the tab, a little faster than it grew. Now click on something that was under the panel. **See**: the click lands on it: no part of the screen is left dead.
12. A finished session. Press the hotkey, pick a workspace, type `say hello` and send it. Keep working in another program. **See**: when the session finishes the tab grows a little by itself (one line, about 380x40) and says which session finished and how its answer starts, then settles back. While it is up, a click just under it still lands on the window below. The keyboard never left your program. No Windows toast, no sound.
13. An approval. Send a task that needs one, for example `create a file called dock-test.txt containing hi` in a workspace whose settings don't already allow writing. **See**: the dock peeks and says what waits: the tool and the file. Hover to open it. **See**: Allow and Deny for that call. Allow it. **See**: the session carries on in the open dock. Move the mouse away before it finishes. **See**: the dock peeks again when it does (while the dock is open nothing peeks: its list shows it).
14. Replying in the dock. Open the dock on a finished session and click into its reply box. **See**: now, and only now, the dock has the keyboard: the caret is in the box and typing lands there. Type `and say goodbye`, send it. **See**: the session runs again, in the dock. Move the mouse away. **See**: the dock shrinks, and the keyboard is back in the program you were in before, without a click.
15. Its links. In the open dock, use the session's link to the chat window. **See**: the chat window, on that session. Copy some text, then use the dock's new-task control. **See**: the pop-up, with that text attached, as from the hotkey.
16. Displays. In Settings > System > Display change the scale of the primary display, then change it back; if there is a second display, unplug it or make it the primary one. **See**: after each change the pill is in the top middle of the display that is primary now, at its right size.
17. The runner goes away. `intuition stop` in WSL. **See**: within about ten seconds the dock is gone, all of it: no empty patch at the top of the screen that swallows clicks. `intuition start`. **See**: within about five seconds the pill is back.
18. The dock switched off. Right-click the tray icon and untick "Show dock". **See**: the dock gone at once, and the Settings window, if open, shows the dock off. `%APPDATA%\intuition-shell\settings.json` is unchanged. Send a task and let it finish. **See**: nothing on screen about it: no dock, no toast; the chat window has it. `intuition shell stop`, then `shell start`. **See**: still no dock, and the checkbox still unticked. Tick it. **See**: the pill back at once.
19. `intuition shell stop`, or Quit in the tray menu. **See**: the tray icon and the dock gone, and the hotkey does nothing.
20. Start on login, from the command: `intuition shell login status`. **See**: `start on login is off`. Then `intuition shell login on`. **See**: `start on login is on`; in Task Manager > Startup apps, an entry named "intuition" or "Electron", enabled; and, if the shell runs, its tray checkbox ticked.
21. From the tray: start the shell, untick "Start on login". **See**: `intuition shell login status` says off, and the entry is gone from Startup apps. Tick it again.
22. `intuition stop` and `intuition shell stop`, then sign out of Windows and in again (or restart). Touch nothing in WSL. **See**: the tray icon within a minute, no console window, the dock once the runner is up, and after some seconds the hotkey opens the pop-up. If a notification said the runner is not running first, note it: ten seconds was too short for WSL to boot.
23. `intuition shell login off` if you don't want it. **See**: `start on login is off`.
24. The snip, one display. With only one display connected (or on the primary one), open something recognisable and press Ctrl+Alt+S. **See**: within about half a second the screen goes slightly darker and freezes: a video stops, the clock doesn't tick; the taskbar is dimmed too; a crosshair; a small dark line at the top, "Drag an area, or click for the whole screen". Nothing flashes first.
25. Drag an area around something. **See**: the area at full brightness with a thin blue edge, its size in pixels small above its top left corner (at 150% scaling, 1.5 times the CSS size you'd expect), and on release a small box just below it with a blinking caret, the workspace you last used in a chip. Type at once, without clicking. **See**: the letters in the box. Drag another area. **See**: the box follows, your text still in it.
26. Switch the workspace: Tab, Shift+Tab, Alt+2, and a click on the chip. **See**: the chip's name changes each time, the caret stays in the box. Shift+Enter. **See**: a new line, the box grows.
27. Enter. **See**: the overlay gone at once, the screen live again; in the chat view a new session in that workspace, your text, and the image attached, which Claude reads (it may ask to read the file: allow it). In `%TEMP%\intuition` a `snip-<time>.png` showing exactly the area, sharp, at the screen's own pixels.
28. Press the key again and press Esc. **See**: gone, nothing started. Press the key again, click once without dragging. **See**: the whole screen selected, the box at its bottom in the middle. Type and press Enter. **See**: a session with the whole screen as its image.
29. A selection near the bottom of the screen, and one in a corner. **See**: the box above the selection, then kept on the screen at the corner, never off it.
30. A second display with another scaling (say 100% beside 150% or 200%). Press the key with the mouse on each in turn. **See**: both frozen, each sharp and lined up with what was there; the box on the display under the mouse takes the typing. Select on the second display and send. **See**: the PNG at that display's own pixels. Drag on one display, then on the other. **See**: the first one's selection goes away.
31. Stop the runner (`intuition stop`) and press the key. **See**: as with the hotkey, no console window; the runner starts within about ten seconds, then the overlays. If not, a notification that the runner is not running.

32. Settings, the migration. Before installing this version, put `"hotkey": "Control+Alt+J"` in `%APPDATA%\intuition-shell\settings.json`. Then `intuition up` with a runner that has the settings API. **See**: Ctrl+Alt+J opens the pop-up. `curl http://127.0.0.1:4777/api/settings` shows `"hotkey": "Control+Alt+J"` under `shell`, and the file holds only `runnerUrl` and `wsl`.
33. Tray > Settings…. **See**: a normal window about 720x640 titled "intuition settings" on the Settings page. Choose Settings… again. **See**: the same window brought to the front, not a second one.
34. In the Settings window, change the hotkey to Ctrl+Alt+K. **See**: at once, without restarting anything, Ctrl+Alt+K opens the pop-up and Ctrl+Alt+Space does nothing. Change the snip hotkey too, and press it. **See**: the snip.
35. Change the hotkey to one another program holds (say Ctrl+Alt+Delete, or a key your other tools use), or to the snip hotkey. **See**: a notification "intuition: the hotkey could not be set" naming it and the one that still works, and the old hotkey still opens the pop-up.
36. Turn the dock off and on in the Settings window, and tick and untick "Show dock" and "Start on login" in the tray. **See**: each change at once, in the tray, the page and on screen, both ways. `intuition shell login status` agrees with the checkbox.
37. Switch the theme to dark, then light, then system. **See**: the chat and Settings windows' title bars and scrollbars follow each time. `intuition stop`, wait, `intuition start`, then change a setting. **See**: it applies within about 15 seconds of the runner being back, with no notification about the socket.
