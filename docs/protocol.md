# Protocol

The runner is one bun process on `127.0.0.1:4777` (`port` in the config file). It serves the web pages, a JSON API and one WebSocket. The types are in [`src/shared/protocol.ts`](../src/shared/protocol.ts): change that file and this one together.

## Pages
| Path | Page |
|---|---|
| `/` | Chat view: sessions in a sidebar, the selected one streaming. `/?session=<id>` opens one. `/?embed=dock` is the same page inside the dock's chat (see "Dock"). |
| `/prompt` | Pop-up prompt: workspace picker and task box, where pasted text and pictures go in at the caret ([D0056](decisions/D0056-pop-up-paste-at-the-caret.md)). |
| `/dock` | The dock: a pill, a peek and an open view of the sessions, with a tab per plugin that is on. See "Dock" and "Plugins". |
| `/settings` | The settings page: every setting of `GET /api/settings`, saved with `PUT /api/settings`. See "Settings". |
| `/assets/<file>` | Files from `src/web/`. |

Pages are plain HTML, CSS and JavaScript modules served from `src/web/` with no build step.

## API
JSON in, JSON out. Errors are `{ "error": "<text>" }` with a 4xx or 5xx status.

| Method and path | Body | Answer |
|---|---|---|
| `GET /health` | | `HealthResponse`: `{ ok: true, version, build }`. `build` is a hash of the code the runner process loaded ([D0011](decisions/D0011-stale-runner-and-shell.md)): `start` and `up` restart a runner whose `build` differs from the repo's. |
| `GET /api/workspaces` | | `WorkspacesResponse`: the config's workspaces and the last one used. Each has `exists` (its folder is there) and `agent`, the agent a new session there runs on (its own `agent`, else the top-level one; see "Agents"): the pop-up's and the snip's agent switch starts on it. |
| `GET /api/sessions?archived=1` | | `SessionsResponse`: the sessions that aren't archived, pinned first, then newest first. With `archived=1`, only the archived ones (same order). 400 for an `archived` other than `0` or `1`. |
| `POST /api/sessions` | `StartSessionRequest` | 201 `SessionResponse`. The turn runs in the background. Remembers the workspace as last used. `agent` (`"claude"` or `"codex"`), when given, runs the session on that agent instead of the workspace's (see "Agents"); any other value is a 400. 400 for an `imagePath` that is refused (see "Clipboard images"), and for `images` that aren't a list of at most 20 pasted pictures (see "Pasted pictures"). |
| `GET /api/sessions/:id/events?after=<seq>` | | `EventsResponse`: stored events with a higher seq (all without `after`). The first request for an imported session reads its history from the transcript first. |
| `POST /api/sessions/:id/messages` | `ReplyRequest` | 202 `SessionResponse`, the session `running`. Stores the reply as a `user` event and runs a turn in the background that resumes the Claude Code session. 404 for an unknown session, 400 for an empty prompt, an `imagePath` that is refused, or `images` as a start refuses them (see "Pasted pictures"), 409 while a turn runs or an approval is open, and 409 `OPEN_IN_TERMINAL` ("it looks open in a terminal: ...") when another process wrote to the session's transcript in the last two minutes, unless the body has `force: true` (see "Terminal sessions"). 400 for a `force` that isn't a boolean. A session in `error` takes a reply too: it resumes its conversation, or starts a new one in the same workspace when it never got a Claude Code session id. |
| `POST /api/sessions/:id/approvals/:approvalId` | `ApprovalRequest` | 200 `SessionResponse`. 404 for an unknown or already answered approval. An `AskUserQuestion` call is allowed only with `answers`, one non-empty answer (at most 4000 characters) per question, keyed by its text; 400 without them, and for `answers` with any other tool or with `deny` ([D0039](decisions/D0039-answering-agent-questions.md)). |
| `POST /api/sessions/:id/rename` | `RenameRequest` | 200 `SessionResponse`. The title is cut as any title (first line, 80 characters); 400 when that leaves nothing. Also the transcript's custom title, so `claude --resume` shows it (see "Managing sessions"). |
| `POST /api/sessions/:id/stop` | `{}` | 200 `SessionResponse` once the interrupted turn has ended (at most 10 seconds): `idle`, with a `stopped` event. 409 `NOT_RUNNING` when the runner runs no turn of the session (a turn arriving from a terminal isn't the runner's to stop). |
| `POST /api/sessions/:id/archive` | `ArchiveRequest` | 200 `SessionResponse`. `archived: true` hides it from the default lists, `false` brings it back. Any session, from the terminal too. 400 for a value that isn't a boolean. |
| `POST /api/sessions/:id/pin` | `PinRequest` | 200 `SessionResponse`. 400 for a value that isn't a boolean. |
| `POST /api/sessions/:id/fork` | `{}` | 201 `SessionResponse`: a new session of the runner's from the conversation so far, idle, titled `<title> (fork)`. 409 while a turn runs, and when the session has no Claude Code conversation yet. |
| `POST /api/sessions/:id/delete` | `{}` | 200 `DeletedResponse` `{ deleted: id }`: the session, its events and its transcript are gone. 409 `TERMINAL_NOT_DELETED` for a session from the terminal (archive it instead), 409 while a turn runs; 500 when the transcript can't be deleted and is still there (the session stays). |
| `POST /api/images` | `ImageUploadRequest` | 201 `ImageUploadResponse`: a picture pasted or dropped into the pop-up, a base64 PNG of at most 15 MB, saved as `<dataDir>/images/<uuid>.png` and answered with its path, to name in `images` (see "Pasted pictures"). 400 for anything that isn't a PNG. |
| `GET /api/images/<uuid>.png` | | A pasted picture (`image/png`), for the chat's thumbnails. 404 for any other name, or a picture that is gone. |
| `GET /api/clipboard` | | The latest `ClipboardCapture`, or `{}` before the first one. The pop-up no longer asks for it (D0056); the shell's self-test does. |
| `POST /api/clipboard` | `ClipboardPostRequest` | 200 the stored `ClipboardCapture`, which replaces the one before (an empty body stores an empty capture). Sent by the Windows shell on the hotkey. `text` is cut to 20,000 characters. 400 for an `imagePath` that is refused, and the capture before it stays. |
| `GET /api/clipboard/image` | | The latest capture's PNG (`image/png`), for the pop-up's thumbnail. 404 when the latest capture has no image or its file is gone. The request names no file. |
| `GET /api/settings` | | `Settings`. See "Settings". |
| `PUT /api/settings` | `SettingsRequest` | 200 the stored `Settings`, after the file is written and the change is in effect. 400 `SettingsErrorResponse` `{ error, field }` naming the first bad field as a dotted path (`"theme"`, `"workspaces.1.path"`, `""` for the body itself); the file is untouched. See "Settings". |
| `GET /api/platform` | | `PlatformResponse`: the layout, the runner, and the shell as it last reported. See "Platform". |
| `GET /api/agents` | | `AgentsResponse`: each agent as `cleat doctor` checks it, Claude Code first: `installed` (its version), `loggedIn`, a `detail` line and a `fix` (empty when it can run). The runner asks `claude --version`, `claude auth status`, and the Codex binary the SDK runs (`--version`, `login status`), at most once every 30 seconds. With the fake agent no command runs and both are ready. The settings page shows it beside the agent choice. |
| `PUT /api/platform/shell` | `ShellReport` | 200 `PlatformResponse`. Sent by the shell. 400 naming the first bad field. See "Platform". |
| `POST /api/platform/open-screen-recording` | `{}` | 202 `SentResponse` `{ sent: true }`: the shell is asked to open System Settings at Screen Recording. 409 `NO_MAC_SHELL` when no shell on macOS is connected. See "Platform". |
| `GET /api/notifications?after=<seq>` | | `NotificationsResponse`: the kept notifications with a higher seq, and the newest seq given out. For a client that polls; the dock gets them on the WebSocket. |
| `GET /api/plugins` | | `PluginsResponse`: every plugin found, loaded or not, built-in ones first, then by id. See "Plugins". |
| `POST /api/plugins/reload` | `{}` | 200 `PluginsResponse`: the plugin files found and imported again (a changed file afresh), and a `plugins` message. |
| `PUT /api/plugins/:id` | `PluginSettingsRequest` | 200 `PluginsResponse`: `enabled` and `hotkey` (an accelerator of at most 80 characters, or `null` for none) written into the config file's `plugins.<id>`, in effect at once, and a `plugins` message. A key left out is unchanged. 404 for an unknown plugin, 400 for an `enabled` that isn't a boolean or a `hotkey` that is empty. |
| `GET /api/plugins/:id/view?fresh=1` | | `PluginViewResponse`: the last view at once, and a new one worked out in the background when there is none, it is older than the plugin's `refreshMs` (after a failed try, only once a minute has passed: `RETRY_MS`), or `fresh=1`; a `plugin_view` message carries it when done. 404 for an unknown plugin, 409 for one that is off, didn't load or has no view, 400 for a `fresh` other than `0` or `1`. |
| `POST /api/plugins/:id/search` | `PluginSearchRequest` | 200 `PluginSearchResponse` `{ query, view }` once the search is done (the query trimmed). 404 for an unknown plugin, 400 for a `query` that isn't a string of at most 500 characters, 409 for one that is off, didn't load or has no search, and 409 `stopped` when a newer search of the same plugin replaced it; 502 with the plugin's error. |

Every `/api/sessions/:id/...` route answers 404 for an unknown session. Rename, stop, archive, pin, fork and delete take a JSON object body (`{}` when there is nothing to say) and pass the port's guard as every route does.

## WebSocket
`GET /ws`. The runner sends `ServerMessage`s; clients send nothing. The shell connects as `GET /ws?client=shell` (see "Platform").
- On connect: `hello` with every session, and `build`: the runner's build id, a hash of the code and the pages it serves (`src/runner/build.ts`). A page remembers the first `build` it was given; a `hello` with another one (the runner was restarted onto new code) reloads the page, so an open window never draws old pages against a new runner ([D0054](decisions/D0054-pages-reload-on-new-build.md)).
- `session` whenever a session's metadata changes (status, title, lastSeq, archived, pinned). `hello` and `session` carry archived sessions too, with `archived: true`: the pages leave them out of their lists themselves.
- `removed` when a session was deleted: its record and events are gone.
- `event` for every stored event, for all sessions. A client that reconnects fetches what it missed with `GET /api/sessions/:id/events?after=<seq>`.
- `delta` for assistant text as it streams. Deltas aren't stored; the complete text follows as an `assistant_text` event, and the client replaces the streamed text with it.
- `settings` with the whole `Settings` after every change (`PUT /api/settings`). Not sent on connect: a client reads `GET /api/settings` when it loads.
- `platform` with the whole `PlatformResponse` whenever the shell's side changes: a report, a shell socket opening, the last one closing.
- `shell_action` (`{ action: "open_screen_recording" }`) only to the shell's sockets, never to the pages' (see "Platform").
- `plugins` with the whole plugin list (`PluginInfo[]`, as `GET /api/plugins`) whenever it changes: loaded again, a plugin turned on or off, a hotkey changed. Not sent on connect: a client reads `GET /api/plugins` when it loads and on each `hello`.
- `plugin_view` (`{ plugin, view: PluginViewResponse }`) each time a plugin's view has been worked out again, or failed to be.
- `notification` for each `Notification`, at the moment it is recorded. None is sent again on connect: a client shows only what arrives while it is connected. It follows the `session` message that carries the status it is about (`waiting_approval`, `idle` or `error`).

## Sessions and events
- A session is one conversation of one agent (Claude Code or Codex, `SessionMeta.agent`) in one workspace. The runner keeps its own id and stores the agent's id for the conversation once known, to resume with it: Claude Code's session id, or Codex's thread id, both in `claudeSessionId`.
- `SessionMeta.agent`: `"claude"` or `"codex"`, set when the session starts and never changed: every reply goes to the same agent. The runner sets it on every session it starts; a session stored before it existed has none and is Claude Code's. One imported from the terminal is `"codex"` when it came from a Codex thread and has none (Claude Code's) otherwise.
- Each turn's SDK messages are reduced to `SessionEvent`s: `user`, `assistant_text`, `tool_use`, `tool_result`, `approval_request`, `approval_resolved`, `auto_denied`, `permission_mode`, `result`, `error`. A turn the person stopped ends with `stopped` instead of `result` or `error`.
- `SessionMeta.permissionMode` is the permission mode the session runs in, as Claude Code reports it (the `init` system message at the start of each turn, and `status` messages when it changes). It is absent until the first turn reports it, and may be a mode other than the two the config allows (for example `"default"` where auto mode is unavailable).
- Status: `running` while a turn runs, `waiting_approval` while at least one approval is open, `idle` after a `result` or `stopped`, `error` after a failed turn.
- `SessionMeta.archived` and `SessionMeta.pinned`: `true` when set, absent otherwise. Neither counts as activity (`updatedAt` stays).
- `SessionMeta.source`: `"cleat"` for a session the runner started, `"terminal"` for one it imported (below). The runner always sends it; a session stored before it existed, or under one of the app's names before the renames ([D0043](decisions/D0043-rename-to-holm.md), [D0048](decisions/D0048-rename-to-cleat.md)), reads as `"cleat"`.
- `SessionMeta.terminalTurn`: `true` while the session is `running` only because its transcript grows (a turn arriving from a terminal), absent otherwise. The pages show "in terminal" for it and keep the reply box on ([D0016](decisions/D0016-synced-sessions-in-the-pages.md)). See "Terminal sessions".
- Stored under the data folder (`~/.local/share/cleat`, or `CLEAT_DATA_DIR`): `sessions.json` for metadata, `events/<id>.jsonl` for events, `state.json` for the last workspace used, `sync.json` for the transcript sync.

## Terminal sessions
Claude Code keeps every session as a transcript under `~/.claude/projects`, the runner's and the terminal's alike. The runner reads them through the SDK (`listSessions`, `getSessionInfo`, `getSessionMessages`) and never writes to them except through its own turns (`query`). The reasons are in [D0015](decisions/D0015-transcript-sync.md).

Codex keeps every thread as a rollout file under `~/.codex/sessions` (`$CODEX_HOME/sessions` when set), the runner's and the terminal's alike, and the runner reads those too, the same way, and never writes under `~/.codex` ([D0031](decisions/D0031-codex-transcript-sync.md)). What differs for a Codex thread is said in each point below; "transcript" means either.
- **Import.** Every 3 seconds the runner lists each workspace's transcripts (its folder only, not its git worktrees). One written in the last 30 days, among the workspace's newest 50, that no runner session owns becomes a session with `source: "terminal"`, status `idle`, `lastSeq` 0, `createdAt` and `updatedAt` from the transcript, and the title from its custom title, else its summary, else its first prompt (cut as any title). Its events are read the first time they are asked for: `GET .../events`, or a reply. A Codex thread counts when its `session_meta` cwd is the workspace's folder (links resolved); it becomes a session with `agent: "codex"`, titled by its name in Codex's `session_index.jsonl` (the TUI's), else its first prompt. A thread Codex started for itself (a subagent's) is not imported. The title follows the transcript only when the transcript's changes: a terminal session renamed in the runner keeps that name until the transcript gives a new one.
- **Events from a transcript.** Each user and assistant message of the main conversation becomes the events a turn gives: `user` (its text), `tool_result`, `assistant_text`, `tool_use`, and a `result` (`ok: true`, the last text) after an assistant message that ended its turn. An event keeps the message's time as `ts`. Subagents' messages and text Claude Code keeps for itself are left out. There are no deltas. A Codex thread's events come from its finished items, as a runner turn of Codex gives them: the person's message is `user`, an agent message `assistant_text`, a command `tool_use` `Bash` with its `tool_result`, a file change `Edit`, an MCP call `mcp__<server>__<tool>`, a web search `WebSearch`; the end of a turn is a `result` with its last message, a failed turn an `error`. Reasoning, and what Codex sends the model without the person seeing it (instructions, the environment), are left out.
- **Live.** When any session's transcript grows while the runner isn't running that session's turn (it was continued in a terminal, say), the new entries are stored as events and sent on the WebSocket, and the session is `running` with `terminalTurn: true`, until 5 seconds after its last entry when that entry is the assistant's or, for Codex, ends the turn (10 minutes after it otherwise); then `idle`. `SessionMeta.terminalTurn` is absent in every other case: any other change of status (a runner turn starting, the end of the live turn, a restart) drops it.
- **One id each.** A transcript the runner owns (any Claude Code session id or Codex thread id its sessions have had) is never imported, and an imported one keeps its runner id across restarts (`sync.json`).
- **Replies.** A reply to any session resumes it through the SDK, as for the runner's own. It first stores what the transcript gained since the last round. When another process wrote to the transcript in the last two minutes (later than 5 seconds after the runner's own last turn of it), the reply is a 409 `OPEN_IN_TERMINAL` unless the body has `force: true`. A session shown `running` only because its transcript grows takes a reply on the same terms; one whose runner turn runs is busy, force or not.
- **In the terminal.** The runner's Claude Code sessions record the entrypoint `cleat`, so Claude Code's resume picker (`claude --resume`, `/resume`) lists them, by the session's title, and `claude --resume <claudeSessionId>` continues them.

## Managing sessions
The person's operations on a session ([D0020](decisions/D0020-session-management.md)). Rename, fork and delete also act on the Claude Code transcript, through the SDK's `renameSession`, `forkSession` and `deleteSession`; archive and pin are the runner's alone.
- **Rename**: the runner's title and the transcript's custom title. The write counts as the runner's own: it neither shows the session running nor makes the next reply a 409 `OPEN_IN_TERMINAL`. A transcript that can't be renamed is logged; the runner's title stands. A terminal session keeps the new title, since the sync reads it back from the transcript.
- **Stop**: open approvals are resolved as `deny`, then the turn is interrupted (the SDK's `interrupt`, and aborted if it hasn't ended 5 seconds later). Nothing the turn says after that is stored; it ends with a `stopped` event and the session `idle`. No notification is recorded.
- **Archive**: hidden from `GET /api/sessions` (listed with `?archived=1`) and from the dock; kept on disk and still on the WebSocket, with `archived: true`.
- **Pin**: listed first.
- **Fork**: the transcript is forked into a new Claude Code session (its custom title `<title> (fork)`), and a new runner session takes it, `source: "cleat"`, `idle`, with a copy of the source's events. Its first reply resumes the fork, not the source. The sync never imports the new transcript as a terminal session.
- **Delete**: only a session the runner started (`source: "cleat"`), between turns. The transcript goes first; then the runner's record and events, and a `removed` message. Its Claude Code ids stay known to the sync, so a transcript left behind is never imported back. A session from the terminal is only archived.
- A turn whose result is in but whose query is still closing counts as over: a reply, a fork and a delete go ahead (fork and delete wait, at most 5 seconds, for it to close), and it never counts as another process writing to the transcript.

The pages: the chat view has a search box (title and workspace, every word, as you type), a workspace filter and an Archived view above the list; each row has a "…" button and a right-click menu (Rename in place, Pin, Fork, Archive, Delete); F2 renames and the Delete key archives the focused row or the session shown, with Undo on a line under the list for six seconds; Delete asks first, in the page, naming the session and saying its transcript goes too; the head has Stop while the runner runs a turn. The dock has Stop in its open view and a right-click menu on rows with Rename, Pin and Archive.

## Agents
A session runs on Claude Code or on OpenAI Codex ([agents](agents.md), [D0029](decisions/D0029-codex-agent.md)). The agent is the request's `agent` (`POST /api/sessions`), else the workspace's own `agent` in the config file, else the top-level one, else `"claude"`. Both give the same events. With Codex:
- Its thread events become `assistant_text` (each agent message, complete), `tool_use` and `tool_result` (a command as `Bash` with `{ command }`, a file change as `Edit` with `{ changes }`, an MCP call as `mcp__<server>__<tool>`, a web search as `WebSearch`), and a `result` (`ok: true`, the last message) or an `error`. It sends no `approval_request`, `auto_denied` or `permission_mode` events; `SessionMeta.permissionMode` is the mode the turn asked for.
- The pages: the pop-up and the snip have an agent switch beside the workspace, on the workspace's `agent` (`GET /api/workspaces`) until flipped (a click, or Alt+A), and send what it shows as `agent`. The settings page sets the top-level and each workspace's `agent` and shows `GET /api/agents`. The chat view and the dock mark each session with its agent's glyph (the name as its tooltip) and name it in the session's head ([D0034](decisions/D0034-agent-choice-in-the-pages.md)).
- The permission mode picks Codex's sandbox: `auto` is `workspace-write` (writes inside the workspace, no network), `default` is `read-only`, both with Codex's `on-request` approval policy. `codex exec` can't ask the host, so no call waits for the person: one the sandbox blocks fails, and the model is told.
- Stop aborts the turn (the `codex` process ends), with a `stopped` event as for Claude Code.
- The transcript sync reads Codex's threads too (see "Terminal sessions"), but rename, fork and delete don't touch them: rename and delete are the runner's alone, fork is a 409.

## Permissions
Each turn asks for the permission mode of its workspace: the workspace's own `permissionMode` in the config file, else the top-level one, else `"auto"` ([D0012](decisions/D0012-auto-mode.md)). Only `"auto"` and `"default"` are accepted; any other value is refused when the config is read. Sessions also load the workspace's own Claude Code settings (user, project and local), so its allow and deny rules apply.
- `auto`: the SDK's classifier allows or denies each call itself, and asks through `canUseTool` only when it can't decide.
- `default`: every call that would prompt asks through `canUseTool`.

A call that reaches `canUseTool`, in either mode, becomes an `approval_request` and waits until the person answers in the chat view. The runner never answers one itself. Denying sends the model a message that the person declined. An `AskUserQuestion` call is answered with the person's answers: allowed, Claude Code gets them as the call's `updatedInput.answers`, and `approval_resolved` stores them as `answers`; denied (Skip), the model is told the questions were skipped.

A call denied without asking (the classifier, a deny rule, the mode: the SDK's `system`/`permission_denied` message) is stored as `auto_denied` with `toolUseId`, `toolName`, `input` (a one-line summary of the call's input, at most 200 characters, when the call's `tool_use` was seen) and `reason` (the deciding component's reason, else the message the model got). Nobody is asked about it.

A session that asked for `auto` and runs in another mode gets one `permission_mode` event (`requested`, `mode`), the first time it is reported, so the person knows why calls come to them. Every change of the mode in effect is logged by the runner.

The pages show `auto_denied` and `permission_mode` as quiet notes, as any kind they don't know.

## Pasted pictures
The pop-up attaches nothing by itself (D0056). A picture pasted or dropped into its task is drawn into a PNG by the page (at most 3000 px on its longer side) and posted to `POST /api/images`, which saves it as `<dataDir>/images/<uuid>.png` and answers its path. The task shows it as a chip, "Image 1", "Image 2" in reading order. A start (`StartSessionRequest`) or a reply (`ReplyRequest`) names the pictures in `images`, in that order, and the prompt names each where it stood as `[Image #n]`. `images` takes at most 20 paths, each a PNG directly in the runner's images folder or one the clipboard rule below takes (a snip); anything else is a 400 (`BAD_IMAGES`).

The prompt the agent sees gets, after the task (and after an `imagePath`'s line), a blank line, `Attached images (read these files):` and a line `[Image #n]: <path>` for each. The stored `user` event keeps `images` apart from the text; the chat draws them as thumbnails from `GET /api/images/<uuid>.png`.

## Clipboard images
The shell saves a clipboard image (and a snip) as a PNG in its OS's temp folder, under `cleat` (`clip-<time>.png` or `snip-<time>.png`, the newest 20 kept), and posts its path. Which paths the runner takes depends on the layout ([platforms](platforms.md)):

- **windows-wsl.** The shell posts a Windows path (`%TEMP%\\cleat\\clip-<time>.png`). The runner turns `C:\Users\x\...` into `/mnt/c/Users/x/...` (drive letter lowercased, backslashes to slashes, normalised) and stores that. An `imagePath` is accepted only when, once converted, it is an existing PNG file named `.png` under `/mnt/<drive>/`; a WSL path that passes the same test is taken as it is. A link is followed and its target must pass too.
- **macos and linux.** The shell and the runner share the machine and its temp folder (`os.tmpdir()`, which is `$TMPDIR` on a Mac and usually `/tmp` on Linux). An `imagePath` is accepted only when it is an absolute path to an existing PNG file named `.png` directly in `<temp>/cleat/`, once links are followed (the folder's own as well: `/var` is `/private/var` on a Mac). The runner stores that real path. A Windows path is refused.

On every layout, anything else (`/etc/passwd`, a path that climbs out with `..`, a missing file, a file that doesn't start as a PNG) is a 400, and the error text names both rules.

The capture is kept in memory only, the latest one. The pop-up no longer asks for it or attaches it (D0056): the shell no longer captures on the hotkey, and its self-test is what posts one now.

A session started, or replied to, with `imagePath` gets the path in the prompt Claude sees, after the task: a blank line, then `Attached image (read this file): <path>`, so Claude reads the file. The stored `user` event keeps `text` and `imagePath` apart. Reading a file outside the workspace is a tool call like any other: it may need the person's approval.

## Notifications
The runner records a `Notification` when a session finishes a turn (`finished`), opens an approval (`needs_approval`) or fails (`error`). Its `title` is the session's; its `body` is one line of at most 140 characters: the start of the answer, the tool and its target (`Write: /path`), or the error's message. Each one is pushed to the WebSocket clients as a `notification` message, which the dock shows as a peek, and the newest 200 are kept in memory for `GET /api/notifications?after=<seq>`. The seq starts at 1 each time the runner starts.

## Dock
The contract between the dock's page and the Windows shell. The shell's half is in [windows-shell](windows-shell.md) ("The dock"), the reasons in [D0008](decisions/D0008-dock.md) and, for the window and the mouse, [D0010](decisions/D0010-dock-fixed-window.md).
- The dock is the page `/dock`, served by the runner, shown by the shell in a frameless, transparent, always-on-top window that touches the top edge of the primary display, centred (on a Mac, centred on the notch or its stand-in: see below).
- **A Mac's notch** ([D0035](decisions/D0035-dock-from-the-notch.md)): on a primary display with one, or with a stand-in on a display without one (180x30 points at the top centre: `dockNotchOf` in `shell/src/os.ts`, [D0037](decisions/D0037-stand-in-notch.md)), the shell centres the window on the notch, on the display's very top edge, and loads `/dock?notch=WxH`, the notch's width and height in CSS pixels (`dockUrl` in `shell/src/origin.ts`; the page reads it with `parseNotch` in `dock-state.js`, and ignores a value that is not a sensible notch). The sizes then follow the notch (`dockSizes`, the same in both files, and a test fails when they differ): idle is the notch and a 76-pixel wing each side (`NOTCH_WING`), at the notch's height; peek is 380 wide and the notch's height plus 40 tall; open is unchanged. In idle the shell takes the mouse on the notch alone, not on the wings, which lie over the menu bar and let clicks through to it; the page counts the pointer on the island there too. The page draws the island in `--notch` black, the notch itself with nothing going on, and the peek's line and the panel below the notch's band.
- **The chat's size** ([D0042](decisions/D0042-chat-in-the-notch.md)): the shell works out how large the island grows into the chat on the primary display (`chatSize` in `shell/src/dock.ts`: 62% by 76% of the area the dock hangs in, at most 1180x860, at least the open dock's 460x480, 24 pixels clear of the sides and the bottom, even numbers) and adds it to the page's address, `&chat=WxH` (`?chat=WxH` without a notch). The page reads it with `parseChat`, and ignores a value smaller than the open dock or larger than 4000. A change of display that changes it loads the page again.
- The window is as large as the largest state, the chat's size (`dockWindow`; `DOCK_WINDOW`, 960x680, for the chat's default size when the page is told none), for its whole life. It is never resized or moved for a change of state. The page fills it, its own background transparent, and draws the island inside it, hanging from the top centre.
- It has four states, and in each the island stays inside a rectangle at the top centre of the window (`DOCK_SIZES`, `islandRect`): idle 128x22, peek 380x40, open 460x480 (out of a notch, see above), and chat, the chat's size. The page may draw less (idle as narrow as its words, open as short as its content), never more. The numbers are in `shell/src/dock.ts` and `src/web/dock-state.js`, and a test fails when they differ.
- The window lets the mouse through everywhere but on that rectangle. The shell decides, from the cursor's position and the state the page last reported; the page is not asked. Until the page has reported a state, and again after a reload, a failed load or a crash, the window lets the mouse through everywhere. While it does, mouse moves still reach the page, so it sees the pointer leave.
- The page decides the state and tells the shell through `window.cleatDock.setState("idle" | "peek" | "open" | "chat")`, the only way out of the page, at once when the state changes, growing or shrinking. The shell changes nothing about the window but where it takes the mouse and whether it can take the keyboard. Every change of shape is the page's own, in CSS, and none waits for the shell. In a normal browser the bridge is absent and the page works the same without it.
- The bridge's one way in is `window.cleatDock.onChat(callback)`: the shell calls it (channel `cleat-dock:chat`) with a session id, or null for the page's own pick, to grow the island into the chat. The page calls `setState("chat")` as for any other change.
- Only in "open" and "chat" can the window take keyboard focus, and on either the shell gives it the keyboard ([D0036](decisions/D0036-dock-keyboard.md)): the page puts it in the reply box, so the person types at once. On a Mac the window is a non-activating panel, so the app the person was in stays active and has the keyboard back when the dock closes. In idle and peek it never takes focus from what the person is doing.
- A second way in, `window.cleatDock.onPlugin(callback)` (channel `cleat-dock:plugin`, [D0057](decisions/D0057-plugins.md)): the shell calls it with a plugin's id when that plugin's hotkey is pressed. The preload passes only an id of lowercase letters, digits and dashes. With the dock off or its page not loaded, the shell shows a notice instead.
- A link to the chat view (`/`, `/?session=<id>`) opened in a new window from any of the shell's pages, and the tray's Open chat, grow the dock into the chat on that session through `onChat`; only with the dock off or its page not loaded do they open the chat window. A link to `/prompt` from the dock opens the pop-up.

What the page does in each state (`src/web/dock.js`; the rules are pure functions in `src/web/dock-state.js`):
- **Idle**, the pill: one line from the sessions on the WebSocket, as wide as its words. `needs you` when any session waits for approval; else `2 running`; else `failed` when the newest session that finished its turn failed; else nothing but a dot, 16 pixels tall and faint (its name for a screen reader is `cleat`). Beside `needs you` or `2 running` a red dot marks that the newest finished one failed.
- **Peek**: a `notification` grows the island to one line, the session's title, the start of the notification's body and `done`, `needs you` or `failed`, for five seconds. One for an approval stays until its session no longer waits or the dock is opened. Others wait their turn behind it, newest last, at most five; a session's newer one replaces its older one that still waits. While the dock is open nothing peeks.
- **Open**: when the pointer has rested on the island for 80 ms, anywhere in the state's rectangle. It closes 400 ms after the pointer left, or at once on Esc or on a press beside it, but not while the pointer is held down, or while the reply box has the person's focus (a click or typing in it; not the focus the dock gave it on opening) or, while the dock has the keyboard, text in it. A press beside it closes it all the same, and once another app has the keyboard a draft no longer holds it; the draft is kept. It lists the sessions, newest activity first, and shows the last 30 events of one: the session peeking when it opened, else the one that peeked last since it was open, else the one it was last left on (remembered in the dock's `localStorage`, `cleat.dock.session`), else the newest that waits for approval, else the newest. A task the person just started from the app (a session the dock had not seen, not from a terminal, created in the last 30 seconds: `justStarted` in dock-state.js) counts as such news: the next opening shows it, and an open dock or chat switches to it at once. ⌘K (Ctrl+K off a Mac) opens the switch with a find field; ⌘1..9 shows the session in that row, and Ctrl+Tab, Ctrl+Shift+Tab, Alt+Down and Alt+Up the next or the one before, in the dock's order: waiting for approval, running, then the rest (D0040). Allow and Deny answer through `POST /api/sessions/:id/approvals/:approvalId`, and the reply box continues the session through `POST /api/sessions/:id/messages`, as in the chat view.
- **Tabs** ([D0057](decisions/D0057-plugins.md), `src/web/dock-plugins.js`): with at least one plugin on (`enabled`, no `error`, a view or a search), the open dock has tabs: Sessions, then one per plugin in the list's order, an icon each with the title (and hotkey) as its tooltip. With a notch they sit in the notch's band on its left wing; without one, a row at the panel's top. A plugin's tab replaces the head, the list and the stream with the plugin's title, a find field when it has a search, Refresh when it has a view, its rows and a status line. A row with a `url` is a link opened in the browser; one with a `task` has Ask, which starts a session on it (`POST /api/sessions`, in the last workspace used, else the first that exists) and grows into the chat on it. Every opening of the dock (the pointer resting on it, a click on a peek) starts on Sessions; only a click on a tab or a plugin's hotkey shows a plugin's tab. Showing a plugin's tab asks `GET /api/plugins/:id/view` again (the runner works out a new view only when the kept one is old) and, from its hotkey or a click, puts the keyboard in its find field. While a plugin's tab shows, the session keys (⌘1..9, Ctrl+Tab, Alt+arrows) do nothing, and text in the find field holds the dock open as a reply does. A plugin's hotkey (`onPlugin`) shows its tab with the keyboard in the find field, after the opening: from idle or a peek it opens the dock, which then stays until the pointer has been on it and left, or Esc; from the chat it steps down to the open dock; pressed while the open dock shows that tab, it closes the dock. Esc closes as on Sessions.
- **Chat** ([D0042](decisions/D0042-chat-in-the-notch.md)): the island grown into the chat view. One click gets there: on the pill or a peek; on the open dock, on the notch's band above its head or on the head away from its controls, on its expand button, or on Open in chat in its "…" (`clickAction` in `dock-state.js`); or the shell's `onChat`. It shows the session the click was about (the one peeking, the one shown) or the dock's usual pick. Its content is the chat view, `/?embed=dock`, in one frame that loads with the dock and stays laid out, out of sight and `inert`, while the dock is in another state. In embed mode that page is dark with no backdrop of its own, opens New task and Settings as windows (target `_blank`), takes the keyboard only while shown, and leaves its history alone. The dock calls `show(id)`, `hide()` and `selected()` on the frame's `window.cleatEmbed` (same origin); the frame says `{ cleatEmbed: "down" }` with `postMessage`, which the dock takes only from that frame on its own origin. Esc that the chat view does not take itself (its search, a menu, a rename, its dialog), its back-to-the-dock button, or a click on the notch's band steps down to the open dock on the session the chat showed, which stays until the pointer has been on it and left, Esc, a press beside it or another app; a second Esc closes it. A press beside the chat, or the window losing the keyboard to another app, closes it to idle. While in the chat nothing peeks.
- **The motion**: the island is one shape whose clip grows out of the pill in 320 ms and shrinks back in 220 ms; the new state's content fades in when the shape is most of the way there. With `prefers-reduced-motion` the shape changes at once and the content fades in.

## Settings
The runner owns the user's settings ([D0022](decisions/D0022-runner-owns-the-settings.md)). They live in its config file (`~/.config/cleat/config.json`, or `CLEAT_CONFIG`), which stays hand-editable; `config.ts` reads them with one zod schema (`SettingsSchema`) and `PUT /api/settings` validates with the same one.

`Settings = { theme, permissionMode, agent, workspaces, shell, port }`:
- `theme`: `"system"` (the default), `"light"` or `"dark"`.
- `permissionMode`: `"auto"` (the default) or `"default"`, and per workspace in `workspaces[].permissionMode` (see "Permissions").
- `agent`: `"claude"` (the default) or `"codex"`, and per workspace in `workspaces[].agent` (see "Agents"). The runner always sends it. A PUT that leaves `agent` out keeps the current one, at the top and on a workspace of the same name, so a client written before it can't reset it; a workspace's `agent: null` clears its own.
- `workspaces`: `{ name, path, permissionMode?, agent? }[]`, names unique, in order: the first is the default when none was used. It may be empty: a new config file has none (the first run and `cleat setup` ask for them), and the pop-up and the snip then say to add one in Settings. `path` is as written in the file (it may start with `~/`).
- `shell`: `{ hotkey, snipHotkey, chatHotkey?, dock, startOnLogin }` or `null`. `chatHotkey` opens and closes the chat in the notch ([D0046](decisions/D0046-chat-hotkey-and-shortcuts-guide.md)); settings written before it have none, and the shell and the pages then use its default (⌘⇧J on a Mac, Ctrl+Alt+J elsewhere; Settings stores it at its next save). The runner only stores it. It is `null` until something sets it: the shell then sends its own local values once (migration) and from then on reads them from the runner.
- `port`: the port the runner serves on. Read-only: a `port` in a PUT body is ignored, and the file's is changed only by hand (a page served on that port can't move it).

`PUT /api/settings` takes a whole `Settings` (a key left out takes its default, as in the file). It refuses, with 400 and the field:
- anything the schema refuses (an unknown theme, mode or agent, an empty name or hotkey, a `dock` that isn't a boolean);
- a workspace name listed twice;
- two of the shell's hotkeys on the same keys (`shell.<the later one>`, "This is already the … shortcut.");
- a workspace `path` that isn't absolute (after `~/`) or isn't an existing folder. A path the current settings already have is not checked again, so a folder that went missing doesn't block other changes.

On success it writes the file atomically (a temp file beside it, renamed over it), keeping every key it doesn't know, at the top and on a workspace of the same name, and the file's `port`. The change is in effect at once: `GET /api/workspaces`, new sessions and the next turn of every session use the new workspaces and modes. Then every client gets a `settings` message. A hand edit to the file applies when the runner restarts, as before; a PUT made before then overwrites the keys it knows.

## Plugins
A plugin is `plugins/<id>/plugin.ts`, built in (the repo's `plugins/`) or the person's own (beside the config file); how to write one is in [plugins](plugins.md), the reasons in [D0057](decisions/D0057-plugins.md). The runner loads them at start and on `POST /api/plugins/reload` (`src/runner/plugins.ts`).
- **`PluginInfo`**: `{ id, title, icon, builtIn, enabled, hotkey, view, search, placeholder, live, tools, error }`. `enabled` is the config's `plugins.<id>.enabled`, else the plugin's own `enabled`, else true for the person's and false for a built-in one, and always false with an `error`. `hotkey` is the config's (`null` there means none), else the plugin's own, else `null`. `view` and `search` say which it has; `placeholder` is its find field's (`null` without a search); `live` that it searches as the person types. `tools` are the MCP tools it declared. `error` is why it couldn't be loaded; such a plugin is listed and never run.
- **`PluginView`**: `{ sections: { title?, rows, empty? }[], note? }`, each row `{ title, detail?, meta?, tone?, url?, task? }`, `tone` one of `accent`, `muted`, `error`. Text only: the pages set it as text, never as markup. The runner cuts what a plugin gives to 20 sections, 200 rows a section and 500 characters a field (80 for a section's title, 60 for `meta`, 8000 for `task`), drops a `url` that isn't `http:` or `https:` and empty fields, and turns anything else into an error.
- **`PluginViewResponse`**: `{ view, at, loading, error }`: the last view and when it was worked out (`null` before the first; kept in `<data>/plugins/<id>/view.json` across restarts), whether a new one is being worked out, and the last try's error (`null` when it worked).
- A `view()` or a search that takes longer than 90 s fails. A plugin's calls to MCP tools go through `src/runner/plugin-agent.ts` only, in a one-off Claude Code process allowed nothing but the plugin's declared tools (`tools: []`, `allowedTools`, `permissionMode: "dontAsk"`, `settingSources: []`, `persistSession: false`, no `canUseTool`).
- The shell registers each hotkey of a plugin that is on, after its own three: never one of them, and a key only once, for the first plugin in the list that asks for it. One it can't register is said once in a notice.
- **The settings page**'s Plugins section lists each plugin with its switch and hotkey (`PUT /api/plugins/:id`; a hotkey that is one of the shell's own or another plugin's is refused in the page), the line "Built in" or "Yours" with its tools in words, or why it can't be loaded, and Reload plugins (`POST /api/plugins/reload`).
- In the config file, `plugins` is `{ "<id>": { enabled?, hotkey?, options? } }`; an entry that is not valid (an id that isn't lowercase letters, digits and dashes, at most 40; a hotkey that isn't a string) is left out with a line in the runner's log; the rest of the file still loads. `options` is handed to the plugin as `ctx.options` and set only in the file; `PUT /api/plugins/:id` keeps it.

## Platform
The settings page's Setup section ([D0025](decisions/D0025-setup-section.md)).
- `GET /api/platform` answers `PlatformResponse = { layout, runner: { running: true, version }, shell: { connected, report } }`. `layout` is `detectLayout`'s (`src/shell/platform.ts`): `windows-wsl`, `macos` or `linux`, `null` only when `CLEAT_PLATFORM` names none. The runner is running, since it answers.
- **The shell's socket.** The shell's settings socket is `/ws?client=shell`. `shell.connected` is true while at least one such socket is open. `shell.report` is the shell's last report with `reportedAt`, kept while it is connected: `null` before the first report and once the last shell socket closed.
- **The report.** `PUT /api/platform/shell` with `ShellReport = { os, startOnLogin, hotkeys: { hotkey, snipHotkey, chatHotkey? }, dockTransparent, screenRecording? }` (`chatHotkey` absent from a shell from before it): the OS the shell runs on (`windows`, `macos`, `linux`); start on login as set now (`null` when it could not be read); whether each hotkey of the settings is registered now; whether the dock is transparent; and on macOS only `systemPreferences.getMediaAccessStatus("screen")` (`granted`, `denied`, `not-determined`, `restricted`, `unknown`), dropped from another OS's report. Unknown keys are a 400. The shell sends it when its socket opens and whenever it changes (a settings change, a Screen Recording check, `--login`, the Settings window getting the focus).
- **Open System Settings.** The page cannot open `x-apple.systempreferences:` links. `POST /api/platform/open-screen-recording` sends `{ type: "shell_action", action: "open_screen_recording" }` to the shell's sockets, which opens its own `SCREEN_RECORDING_PANE`; no URL is sent. 409 `NO_MAC_SHELL` when no shell is connected or its report is not from macOS.
- **The page** draws one line each for the layout, the runner, the shell, start at login and the shortcuts (once the shell has reported), the dock when it is opaque, and on macOS Screen Recording with an Open System Settings button while it is not allowed. A line that is not ok says what to do (`setupLines` in `src/web/settings-model.js`). The runner shows as not reachable while the page's socket is closed.

## Guarding the port
The runner binds `127.0.0.1` only. A web page in any browser can still send requests to a local port, so every request is checked:
- `Host` must be `127.0.0.1:<port>` or `localhost:<port>`.
- A request with an `Origin` header must have the runner's own origin. The WebSocket upgrade is checked the same way.
- `POST` and `PUT` bodies must be `content-type: application/json`.

## Test hooks
- `CLEAT_CONFIG`: path of the config file. `CLEAT_DATA_DIR`: the data folder. `CLEAT_PORT`: the port (0 picks a free one).
- `CLEAT_FAKE_AGENT=1`: sessions run against a scripted fake instead of Claude Code, so tests and CI need no login. A plugin's `ctx.tool` then answers `{ fake: true, tool, args }` and `ctx.ask` `{ fake: true, prompt }` (`fakePluginAgent`); tests give their own with `startServer`'s `plugins` argument (`agent`, `builtInDir`). The fake is described where it is defined, in `src/runner/`.
  With the fake agent the runner reads no transcripts, Claude Code's or Codex's; tests give the sync their own (`startServer`'s `sync` argument: `transcripts` for Claude Code, `codex` for Codex, e.g. `codexThreads(<temp CODEX_HOME>)`). Nor does it rename, fork or delete any: a fork is a new fake conversation that remembers the old one's prompts; tests give their own (`startServer`'s `ops` argument).
